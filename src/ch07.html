How to answer any design question

  1. Clarify requirements. Functional: what must it do? Non-functional: offline use, latency, battery, minimum SDK, number of users and data volume? Constraints: team size, deadline, existing code.
  2. High-level design. Layers, main components, and the data flow, such as UI, ViewModel, domain, repository, then local and remote sources.
  3. Deep-dive into the one or two riskiest parts: sync, concurrency and failure handling.
  4. Trade-offs. “Option A gives X but costs Y. Because our constraint is Z, I would choose A, and I would revisit if …”
  5. Failure and evolution. What breaks first, how you would monitor it, and how it grows.

Avoid: naming a pattern before you know the requirement. “I would use Clean Architecture” is not an answer. Say “it depends on …”, and then say what it depends on. Tie your claims to real experience from your projects.

1. Design a scalable Android application

“Scalable” covers the codebase (team growth), performance (data and users) and features (changing safely).

Design

  • Layers: UI in Compose, then a ViewModel holding UI state, then an optional domain layer of use cases, then a data layer with repositories, Room and Retrofit. Unidirectional data flow, with one source of truth.
  • Modularisation by feature when team size or build time demands it. Hilt for DI. Coroutines and Flow throughout.
  • Offline-first data, Paging for large lists, image caching, and background work through WorkManager.
  • Engineering at scale: CI with unit, UI and benchmark tests, feature flags, staged rollouts, crash, ANR and performance monitoring, and Baseline Profiles.
ChoiceBenefitCost
Single moduleSimple and fast to startSlow builds and tangled code as it grows
Many modulesIsolation, parallel builds, clear ownershipConfiguration overhead, and discipline needed
Extra layers (domain, mappers)Testable, replaceable data sourcesBoilerplate, which is wasteful in small apps

Say: “I would start with the simplest structure that supports the stated scale, with clear seams at the boundaries, so I can split things later without a rewrite.” Pitfall: premature over-engineering is as bad as a single giant Activity.

3. Handle offline data

Design

Room is the source of truth, and the UI observes it. For reads, show cached data immediately and refresh in the background. For writes, save locally first (optimistic), mark the row as pending, and sync later with WorkManager, which handles network constraints, backoff and unique work. Use idempotent writes through client-generated IDs.

Decide per feature what must work offline, because not everything needs to. Pitfalls: unbounded cache growth without an eviction policy, migrations that break users' data, sensitive data stored unencrypted, and no UI signal for pending or failed sync.

4. Design the repository layer

Design

  • The interface lives in domain and describes what the app needs. The implementation lives in data and describes how. It hides remote, local and cache sources, and the mapping between DTOs, entities and domain models.
  • Expose a Flow for data that changes over time, and suspend functions for one-shot actions. Keep them main-safe by injecting the dispatcher.
  • Error model: typed results or sealed errors, such as Network, Unauthorized, NotFound and Unknown. Raw exceptions should not leak into the UI.
  • The cache policy is explicit and testable.
Cache policyBehaviourTrade-off
Cache firstUse local data if it existsFast, but may be stale
Network firstFetch, and fall back to the cache on failureFresh, but slow when the network is poor
Stale while revalidateShow the cache, refresh, then update the UIBest experience, more logic
interface FeedRepository {
    fun observeFeed(): Flow<List<Post>>     // backed by Room
    suspend fun refresh(): Outcome<Unit>     // network into Room; returns a typed error
}

Pitfalls: a generic Repository<T> that fits nothing well, leaking Retrofit or Room types upward, one giant repository, and swallowing CancellationException. One repository per aggregate or feature is a good default.

5. Handle API failures and retries

Design

  1. Classify errors: transient (timeouts, connection resets, 502, 503, 429), permanent (400, 403, 404, parse errors), and authentication (401).
  2. Retry only transient errors, with exponential backoff, jitter, a maximum number of attempts, and a cap. Respect Retry-After for 429.
  3. Retry only idempotent requests such as GET, PUT and DELETE. For POST, use an idempotency key.
  4. On 401, refresh the token once. Serialise refreshes with a Mutex, so concurrent calls do not all refresh at the same time, then replay the request. If the refresh fails, log the user out.
  5. UX: show cached data with a banner, give a clear retry action, and never show an endless spinner. Queue user writes for WorkManager.
  6. Protect the backend: jitter, a circuit breaker or fail-fast behaviour when a service is down, and timeouts everywhere.
suspend fun <T> retry(times: Int = 3, baseDelay: Long = 500, block: suspend () -> T): T {
    var delayMs = baseDelay
    repeat(times - 1) {
        try {
            return block()
        } catch (e: IOException) {
            delay(delayMs + Random.nextLong(0, delayMs / 2))  // backoff with jitter
            delayMs *= 2
        }
    }
    return block()   // the last attempt lets the error propagate
}
ChoiceTrade-off
Aggressive retriesHigher success rate, but battery drain, latency and retry storms
Few or no retriesPredictable and gentle on the server, but more failures are visible

Pitfalls: blind retries of non-idempotent POST requests, which can create duplicate orders. Retrying 4xx errors. Every client retrying in lockstep. Logging request bodies that contain personal data.

6. Handle concurrency

Design

  • Structured concurrency: work lives in viewModelScope or lifecycleScope. App-level work uses an injected application scope. Work that must be guaranteed to run uses WorkManager.
  • Prefer not to share mutable state. If you must share it, protect it: one owner with StateFlow.update {}, a single-thread dispatcher, a Mutex, atomic values, or Room transactions.
  • Inject dispatchers. Make suspend functions main-safe. Use flatMapLatest or debounce to avoid stale and duplicate requests. Handle cancellation cooperatively.
ToolUseCost
MutexProtect a critical section that spans suspension pointsContention; do not hold it across slow I/O
Single-thread confinementAll access happens on one threadSerial work, which can become a bottleneck
Atomic or update {}Simple counters and small stateOnly suitable for small state
Channel or actor styleSerialise commandsMore design complexity

Races to name: double-tapping a submit button, responses arriving out of order, a token-refresh stampede, read-modify-write on shared state, and the UI collecting after the screen has gone. Say: “I design so the races cannot happen, then add synchronisation only where sharing is unavoidable.”

7. Support different device configurations

Design

  • Dimensions to cover: screen size, foldables, tablets and ChromeOS; orientation; density; font scale; locale and right-to-left layouts; dark mode; API level; RAM and CPU tier; and hardware features.
  • Adaptive layouts driven by WindowSizeClass, such as list-detail on wide screens. Choose layouts by window size, not by device model. Do not lock orientation as a shortcut.
  • State survives changes: ViewModel, rememberSaveable and SavedStateHandle.
  • Check capabilities rather than assume them: hasSystemFeature() and Build.VERSION.SDK_INT guards behind small wrappers, with a graceful fallback.
  • Test matrix: emulators plus a few real low-end and foldable devices, Firebase Test Lab, screenshot tests for font scale, dark mode and right-to-left, and Vitals for real-device data.
DecisionTrade-off
Lower the minimum SDKMore users, but more compatibility code and testing
Full adaptive UIBetter tablet and foldable experience, with extra design and QA cost
Feature tiers for low-end devicesSmooth on weak hardware, but more variants to maintain

Pitfalls: hard-coded dp sizes and strings, an untested 200% font scale, assuming a camera, NFC or sensor exists, and state lost on rotation or when a foldable opens or closes.

8. Make an application testable

Design for it

  • Constructor injection and interfaces at boundaries. No hidden singletons or static calls.
  • Pure Kotlin domain logic with no Android classes. Inject dispatchers and the clock.
  • Unidirectional state, with UiState going in and events coming out, so UI tests assert on state.
LevelWhat is testedTools
Unit (many)Domain logic, ViewModels, mappersJUnit, runTest, Turbine, fakes
IntegrationRepository with Room and a mock serverIn-memory Room, MockWebServer
UIComposables and flowsCompose test rule, Espresso, Hilt test modules
Screenshot and benchmarkVisual and performance regressionsPaparazzi or Roborazzi, Macrobenchmark
End-to-end (few)Critical user journeysFirebase Test Lab

Trade-offs: fakes versus mocks. Fakes test behaviour and survive refactoring. Mocks verify interactions but break when code is refactored. Chasing a coverage percentage is less useful than testing risky logic. Flaky UI tests cost the team trust, so keep the pyramid bottom-heavy. Pitfall: tests coupled to implementation details.

9. Approach a major architecture migration

Examples: XML to Compose, RxJava to coroutines and Flow, MVP to MVVM, or a monolith to modules.

Plan

  1. Why, and how we will know: set concrete goals and metrics, such as build time, crash rate or delivery speed. If it cannot be measured, question the migration.
  2. Migrate incrementally, not with a big-bang rewrite (a strangler approach). New code uses the new style. Old code is migrated by value and risk, with interop adapters such as ComposeView or asFlow().
  3. Guardrails so the old pattern stops growing: lint or detekt rules, a review checklist and templates.
  4. Safety: feature flags, staged rollouts, tests before behaviour changes, and a rollback plan.
  5. People: an RFC or ADR, documentation, pairing, and an agreed timeline. Keep delivering features alongside the migration.
  6. Track and finish: a migration dashboard showing the percentage migrated. Delete the old code. Do not leave two systems running forever.
ApproachProsCons
Big-bang rewriteA clean slateLong freeze, high risk, regressions
IncrementalContinuous value, low riskDual maintenance; needs discipline to finish
Do not migrateZero riskGrowing tech debt, and hiring and tooling pain

Pitfalls: migrating because a pattern is fashionable, having no end date so the migration stays half-finished forever, and changing behaviour and architecture in the same pull request.

10. Make technical decisions when several solutions exist

A framework for deciding

  1. Define the problem and the decision criteria: user impact, complexity, time, team skills, maintainability, performance, risk, and the cost of reversing the decision.
  2. List two or three realistic options, including “keep what we have”.
  3. Use evidence over opinion: a small spike or prototype, a benchmark, and a check of library health (maintenance, community, Google support).
  4. Classify the decision. A two-way door is easy to reverse, so decide quickly. A one-way door is costly to reverse, so analyse it carefully and seek review.
  5. Write it down in an ADR or RFC, invite feedback, decide, then commit, even if someone disagrees. Set a trigger for when to revisit.
Example decisionCriteria that usually decide it
Room vs SQLDelightTeam familiarity, Kotlin Multiplatform plans, query complexity
Hilt vs KoinCompile-time safety and scale, against simplicity
Compose vs XML for a new screenTeam skills, existing UI, interop cost
Build vs buy an SDKControl, size and privacy cost, time to market

Say: “I optimise for the team's long-term velocity and the user's outcome, not for the technology I happen to like.” Have one real example ready where data changed your mind.
