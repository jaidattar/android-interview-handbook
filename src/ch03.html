1. launch vs async

Often asked as: “Which one returns a result?”, “How do exceptions differ?”, “How do you run two calls in parallel?”

What is the difference?

  • launch returns a Job and is fire-and-forget, with no result.
  • async returns a Deferred<T>, which is a Job that carries a result. You get the value with await(). Use it for parallel decomposition.

Both start eagerly by default. start = CoroutineStart.LAZY delays the start until start() or await() is called.

suspend fun loadScreen() = coroutineScope {
    val user = async { api.user() }      // both run in parallel
    val feed = async { api.feed() }
    Screen(user.await(), feed.await())   // total time is the max, not the sum
}

How do exceptions behave?

launch propagates the exception to its parent immediately, which leads to the handler or a crash. async also cancels the parent in a normal scope, but the exception is rethrown at await(). Under supervisorScope, an async failure is delivered only at await().

Trap: calling async { }.await() immediately is just sequential code with extra overhead. For one call, use withContext. The right parallel pattern is to start all the async blocks first, then await them together with awaitAll(). Do not await inside the map itself.

2. coroutineScope vs supervisorScope

Often asked as: “If one child fails, what happens to its siblings?”, “SupervisorJob vs Job”.

coroutineScopesupervisorScope
A child failsCancels siblings and the scope, then rethrowsSiblings keep running; the failure belongs to that child
Waits for childrenYesYes
Where you handle failurestry/catch around the scope callInside each child (try/catch or a handler)
supervisorScope {
    launch { runCatchingCancellable { syncA() } }   // may fail on its own
    launch { syncB() }                              // unaffected by syncA
}

What is a SupervisorJob?

A Job where a child's failure does not propagate to the parent or to siblings. viewModelScope is built as SupervisorJob() + Dispatchers.Main.immediate. Watch the placement: launch(SupervisorJob()) { … } is a bug, because the new supervisor replaces the parent and breaks the structure. Pass the supervisor to the scope, not to the child builder.

Follow-up: both forms suspend until every child finishes. Scope functions never return early. A failing async child inside supervisorScope does not cancel its siblings, but you must handle the failure at await().

3. Structured concurrency

Often asked as: “What is it, and why does it matter?”, “Why avoid GlobalScope?”, “How does the Job hierarchy work?”

Explain it.

Every coroutine runs inside a CoroutineScope and becomes a child of that scope's Job. The rules are:

  • A parent does not complete until all its children complete.
  • Cancelling a parent cancels all of its children.
  • A child's failure cancels the parent and its siblings, unless the hierarchy is supervised.

The result: no leaked work, no forgotten threads, errors always reach someone, and the lifetime of the work is tied to a component such as viewModelScope or lifecycleScope.

What is a CoroutineContext?

An indexed set of elements: a Job, a Dispatcher, a CoroutineName and a CoroutineExceptionHandler, combined with +. A child inherits the parent's context but gets its own new Job. Elements passed to the builder override the inherited ones.

val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default + CoroutineName("sync"))
scope.launch { /* ... */ }
scope.cancel()            // cancels everything; this scope cannot be reused
// GlobalScope.launch { } is unstructured and lives as long as the process: avoid it

Trap: creating a CoroutineScope(...) inside a class and never cancelling it is a leak. In Android, use lifecycle-bound scopes. For app-wide work, inject an application scope, or use WorkManager if the work must survive the process.

4. Dispatchers: Main, IO and Default

Often asked as: “Which one for what?”, “What are the thread pool sizes?”, “withContext”, “Main.immediate”.

DispatcherUse forThreads
MainUI updates and light workThe single main thread
IOBlocking I/O: network, disk, database, filesElastic, up to 64 (or the core count, if higher)
DefaultCPU-bound work: sorting, parsing, diffing, bitmap workEqual to the number of CPU cores (minimum 2)
UnconfinedRare; tests and special casesRuns in the caller's thread until the first suspension

What are the key facts?

  • Dispatchers.IO and Default share the same thread pool, so switching between them is often cheap.
  • withContext(Dispatchers.IO) { } switches, suspends until the block completes, then returns to the caller's dispatcher. Suspend functions should be main-safe: callers should not need to know which dispatcher to use.
  • Dispatchers.Main.immediate runs inline when already on the main thread. That is why viewModelScope state updates can appear synchronously.
  • limitedParallelism(n) gives a bounded view, for example IO.limitedParallelism(1) for a serial database writer.
suspend fun parse(json: String) = withContext(Dispatchers.Default) { heavyParse(json) }

class Repository @Inject constructor(
    @IoDispatcher private val io: CoroutineDispatcher   // injected, so tests can replace it
)

Trap: blocking calls such as Thread.sleep, JDBC or runBlocking on Default starve CPU work. On Main they cause ANRs. Hard-coded dispatchers make tests flaky: inject them and use StandardTestDispatcher with runTest.

5. Exception handling

Often asked as: “Why doesn't my try/catch catch this?”, “CoroutineExceptionHandler”, “CancellationException”.

How are exceptions propagated?

  • launch: an uncaught exception propagates up to the root, then reaches the CoroutineExceptionHandler, or crashes the app.
  • async: the exception is stored in the Deferred and thrown at await(). In a normal scope it still propagates to the parent.
  • try { launch { throw X() } } catch does NOT work, because the exception happens in the child, not in the call to launch. Put the try/catch inside the coroutine.
viewModelScope.launch {
    try {
        repository.refresh()
    } catch (e: CancellationException) {
        throw e                                   // never swallow cancellation
    } catch (e: IOException) {
        _ui.update { it.copy(error = e.message) }
    }
}

val handler = CoroutineExceptionHandler { _, e -> log(e) }   // last resort, root coroutines only
scope.launch(handler) { /* ... */ }

What about CancellationException?

It is how cancellation is signalled, and it is not treated as a failure. It does not cancel the parent and it does not reach the handler. Catching Exception or Throwable, or wrapping suspend calls in runCatching, swallows it, and the coroutine keeps running after it was cancelled. Always rethrow it.

Follow-up: CoroutineExceptionHandler works only on the root coroutine, or a direct child of a supervisor, and not on async. For cleanup use finally. If the cleanup itself suspends, wrap it in withContext(NonCancellable). In Flow, use .catch {} (which catches only upstream errors) and onCompletion.

6. StateFlow vs SharedFlow

Often asked as: “When do you use each?”, “replay and buffer”, “Why was my event lost?”. Chapter {{ch:2}} covers the basics; this is the internals.

StateFlowSharedFlow
What it isA SharedFlow with replay 1, conflated and deduplicatedA general hot stream
Initial valueRequiredNone
ConfigurationNonereplay, extraBufferCapacity, onBufferOverflow
Has .valueYes, readable and writableNo, use tryEmit or emit
Use forStateEvents

What are the gotchas?

  • StateFlow skips equal values (it uses equals), and a slow collector can miss intermediate values because of conflation. That suits state, but not “every click”.
  • A SharedFlow with replay = 0 and no subscribers drops the emission. emit suspends only when a configured buffer is full.
  • stateIn(scope, WhileSubscribed(5000), initial) and shareIn convert a cold Flow into a hot one.
private val _events = MutableSharedFlow<Event>(
    extraBufferCapacity = 1,
    onBufferOverflow = BufferOverflow.DROP_OLDEST
)
val events = _events.asSharedFlow()

_state.update { it.copy(loading = false) }   // atomic read-modify-write

Trap: _state.value = _state.value.copy(...) from several coroutines can lose updates. Use update {}. Neither type is lifecycle-aware on its own, so collect them with repeatOnLifecycle.

7. Cold Flow vs hot Flow

Often asked as: “What starts a Flow?”, “Does each collector get its own execution?”, “What does flowOn do?”

Cold: flow {}, flowOf, asFlowHot: StateFlow, SharedFlow, channel-based
When it startsOnly when collectedActive regardless of collectors
Per collectorEach collector re-runs the producerCollectors share one producer
CompletesYes, when the block endsNever (StateFlow and SharedFlow)
ExamplesA Room query, a network callUI state, an event bus
val cold = flow { emit(api.fetch()) }          // 2 collectors = 2 network calls
val hot = cold.shareIn(
    viewModelScope, SharingStarted.WhileSubscribed(5_000), replay = 1
)                                               // 2 collectors = 1 network call

// flowOn changes only the UPSTREAM operators:
flow { emit(compute()) }.flowOn(Dispatchers.Default)

Any other points?

  • flowOn affects only the operators upstream of it. Never use withContext around emit: that breaks context preservation and throws.
  • Flow is sequential by default. buffer() and conflate() decouple producer and consumer. flatMapLatest, combine and zip compose flows.
  • callbackFlow { …; awaitClose { unregister() } } wraps callback APIs. Always call awaitClose, or the flow ends immediately and the listener leaks.

Trap: exposing a cold Flow from a ViewModel to the UI means every re-collection restarts the work. Convert it to a StateFlow with stateIn.

8. collect vs collectLatest

Often asked as: “What happens to a slow collector?”, “search as you type”, “conflate vs collectLatest”.

What is the difference?

  • collect { } processes every value, one after another. A slow block makes the producer wait, which is backpressure through suspension.
  • collectLatest { }: when a new value arrives, the running block for the previous value is cancelled and restarted with the new value. Only the latest value is fully processed.
queryFlow
    .debounce(300)
    .distinctUntilChanged()
    .collectLatest { query -> showResults(repository.search(query)) }  // old search cancelled

// The same idea as an operator:
queryFlow.flatMapLatest { repository.searchFlow(it) }
// conflate() skips intermediate values but does NOT cancel the running block
OperatorBehaviour with a slow consumer
collectThe producer suspends; every value is processed in order
buffer()The producer runs ahead, and values are queued
conflate()Drops intermediate values and keeps the newest; the current block finishes
collectLatestCancels the current block when a newer value arrives

Trap: do not use collectLatest when the block must finish, such as saving to a database, sending analytics or processing a payment. It would be cancelled halfway. The work inside the block must also reach a suspension point for cancellation to take effect.

9. Cancellation and lifecycle-aware collection

Often asked as: “How does cooperative cancellation work?”, “repeatOnLifecycle vs launchWhenStarted”, “collection in Compose”.

How does cancellation work?

Cancellation is cooperative. job.cancel() marks the Job as cancelled. The coroutine stops at the next suspension point that checks for it, such as delay, yield, withContext, Flow operators or ensureActive(). A tight CPU loop never stops on its own unless it checks isActive or calls ensureActive().

launch(Dispatchers.Default) {
    for (file in files) {
        ensureActive()                     // cooperative check inside the loop
        process(file)
    }
    try {
        doWork()
    } finally {
        withContext(NonCancellable) { cleanup() }   // cleanup still runs after cancel
    }
}
withTimeout(3_000) { api.call() }            // throws TimeoutCancellationException
withTimeoutOrNull(3_000) { api.call() }      // returns null instead

Blocking calls such as Thread.sleep or a blocking InputStream.read are not cancellable by themselves.

How do you collect lifecycle-aware?

Collecting inside lifecycleScope.launch { flow.collect {} } keeps collecting while the app is in the background, which wastes resources and keeps hot upstreams active. The correct patterns are:

// Views
viewLifecycleOwner.lifecycleScope.launch {
    viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        launch { viewModel.ui.collect(::render) }      // one launch per flow
        launch { viewModel.events.collect(::handle) }
    }
}
// Compose
val ui by viewModel.ui.collectAsStateWithLifecycle()

repeatOnLifecycle cancels its block at STOP and relaunches it at START. The older launchWhenStarted only suspends, so the upstream stays active, and it is deprecated. Combine this with WhileSubscribed(5000) in the ViewModel, so the upstream stops when the UI is gone but survives rotation.

Trap: inside repeatOnLifecycle, the first collect never returns, so a second collect placed after it never runs. Use separate launch blocks. In Fragments, use viewLifecycleOwner, not this. Test cancellation with runTest and advanceTimeBy.
