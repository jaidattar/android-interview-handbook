How to answer “How do you optimise recomposition?”

A common opener in senior interviews. Say it in this order, and keep it to about 90 seconds.

Model answer

  1. Measure first. Do not optimise blindly. Use Layout Inspector recomposition counts, system tracing or Perfetto, and the Compose compiler reports. Always measure a release build with R8, because debug builds are much slower and can mislead you.
  2. Keep composables small and focused. The recomposition scope is the nearest restartable composable. Small functions limit the blast radius of a state change.
  3. Read state as late as possible. Reading state high in the tree recomposes everything below it. Lambda-based modifiers such as Modifier.offset { }, graphicsLayer { } and drawBehind { } skip composition and redo only layout or drawing.
  4. Use stable data models. Immutable val properties, @Immutable or @Stable where justified, and ImmutableList instead of List. Strong skipping is the default from Kotlin 2.0.20 onwards, and a stability configuration file covers third-party classes.
  5. Remember expensive work. For example remember(list) { list.sortedBy { it.name } }. Do not allocate inside composition on every pass.
  6. Use derivedStateOf when the input changes far more often than the output you need, such as scroll position driving a “show button” flag.
  7. Give lazy items stable keys. Use key = { it.id } and contentType, so items are reused and moves do not recompose everything.

Closing line: “The goal is not zero recompositions. It is skipping the expensive ones. I fix what the profiler shows.”

Follow-up: why does a composable with a List<Item> parameter recompose? A List is an interface the compiler cannot prove immutable, so it is unstable. Without strong skipping the function is never skipped. With strong skipping it is skipped only when the same instance is passed (===).

1. Recomposition and stability

Often asked as: “What triggers recomposition?”, “What is a stable type?”, “How do you read the Compose compiler reports?”

What is recomposition?

Compose re-executes only the composables that read a State whose value changed, to update the UI tree. Composables must be idempotent and free of side effects, because they can run in any order, run many times, be skipped, or run in parallel. A composable is skipped when all of its parameters are unchanged, provided it is skippable.

What does “stable” mean?

A type is stable if equal instances stay equal, changes to its public properties notify Compose, and all of its public properties are stable too. Stable types include primitives, String, function types, State, classes with only val stable properties, and types marked @Stable or @Immutable. Unstable types include List, Set and Map, classes with var properties, and classes from modules not compiled with the Compose compiler.

Trap: @Stable and @Immutable are promises that the compiler trusts. Breaking them causes stale UI. Mutating a mutableListOf in place does not notify Compose: use mutableStateListOf, or emit a new list.

2. remember vs rememberSaveable

Often asked as: “What survives rotation?”, “What can rememberSaveable store?”, “How does it compare with a ViewModel?”

rememberrememberSaveable
RecompositionSurvivesSurvives
Configuration changeLostSurvives (stored in a Bundle)
Process deathLostSurvives
Allowed typesAnythingBundle-compatible types, Parcelable, Serializable, or a custom Saver

How do you choose?

  • remember: cached objects and calculations, animation state, and anything cheap to rebuild. remember(key1) { } recalculates when a key changes.
  • rememberSaveable: UI state the user would be annoyed to lose, such as text field input, the selected tab, or scroll position (rememberLazyListState already saves it).
  • ViewModel: screen-level state and business logic. It survives rotation but not process death, so add SavedStateHandle for what must survive that.
var query by rememberSaveable { mutableStateOf("") }
val total = remember(items) { items.sumOf { it.price } }   // recalculated only when items changes
var filter by rememberSaveable(stateSaver = FilterSaver) { mutableStateOf(Filter()) }

Trap: remember forgets its value when the composable leaves the composition. In a LazyColumn without keys, that happens when an item scrolls off screen. The Bundle has a size limit of about 1 MB shared per transaction, so never store large lists or bitmaps in it.

3. LaunchedEffect vs DisposableEffect

Often asked as: “Which effect for which job?”, “How do the keys behave?”, “rememberUpdatedState”.

What is the difference?

  • LaunchedEffect(key): runs a suspend block in a coroutine tied to the composition. It is cancelled when it leaves the composition, and cancelled and relaunched when the key changes. Use it for one-off loads, collecting flows, animations, and showing snackbars.
  • DisposableEffect(key): for non-suspending setup that needs cleanup, such as registering listeners, receivers or lifecycle observers. onDispose { } is mandatory and runs when the key changes or the composable leaves.
LaunchedEffect(userId) { viewModel.load(userId) }               // restarts when userId changes
LaunchedEffect(Unit) {                                          // runs once
    viewModel.events.collect { snackbarHost.showSnackbar(it) }
}

DisposableEffect(lifecycleOwner) {
    val observer = LifecycleEventObserver { _, event ->
        if (event == Lifecycle.Event.ON_RESUME) viewModel.refresh()
    }
    lifecycleOwner.lifecycle.addObserver(observer)
    onDispose { lifecycleOwner.lifecycle.removeObserver(observer) }
}

What are the other effect APIs?

  • SideEffect: runs after every successful recomposition. Use it to publish Compose state to non-Compose code.
  • rememberCoroutineScope: launches work from event handlers such as onClick, not from the composition itself.
  • rememberUpdatedState(x): when a long-running effect needs the latest value or lambda without restarting.
  • produceState turns non-Compose async data into a State. snapshotFlow { state } turns State into a Flow.

Trap: wrong keys. LaunchedEffect(Unit) that captures a changing value uses a stale one, and LaunchedEffect(true) has the same problem. Never run side effects, such as network calls or writes, directly in the composable body.

4. derivedStateOf

Often asked as: “When does it help, and when is it pointless?”, “How does it compare with remember(key)?”

What does it do?

It creates a State computed from other states. It notifies readers only when the result changes, not every time an input changes. It is ideal when the input changes far more often than the output.

val listState = rememberLazyListState()
val showScrollToTop by remember {
    derivedStateOf { listState.firstVisibleItemIndex > 0 }
}
// firstVisibleItemIndex changes constantly, but showScrollToTop flips only once or twice
AnimatedVisibility(showScrollToTop) { ScrollToTopButton() }

When should you not use it?

  • When the output changes as often as the input, as in derivedStateOf { a + b }. It only adds overhead.
  • When the inputs are not Compose State (plain parameters): use remember(key) { }. derivedStateOf itself must be wrapped in remember.
  • When the calculation is cheap. Recomputing is cheaper than tracking.

Follow-up: remember(a, b) { calc } recalculates when the keys change, based on equality of the parameters. derivedStateOf tracks the State reads inside its lambda. You can combine them: remember(threshold) { derivedStateOf { x > threshold } }.

5. LazyColumn performance

Often asked as: “Why is my list janky?”, “keys and contentType”, “nested scrolling”.

How do you keep a long list smooth?

  • A stable, unique key per item. It keeps item identity across reorders and inserts, preserves item state and enables animations. contentType lets Compose reuse compositions of the same layout type.
  • Stable, immutable item models, so unchanged rows are skipped.
  • No heavy work or allocations inside item composables. Precompute in the ViewModel or with remember.
  • Read frequently changing state, such as scroll offset, through derivedStateOf or lambda-based modifiers.
  • Load images with Coil or Glide at a fixed size. Use Modifier.animateItem() for item animations.
  • Use Paging 3 (collectAsLazyPagingItems()) for large or remote data.
  • Test in release mode, and add Baseline Profiles to reduce jank during the first scroll.
LazyColumn(state = listState) {
    items(items = products, key = { it.id }, contentType = { it.type }) { product ->
        ProductRow(product, onClick = onProductClick)   // a lambda that does not capture changing state
    }
}

Trap: do not nest a LazyColumn inside a verticalScroll or another lazy list in the same direction. That causes an infinite-height crash, or composes every item. Use one lazy list with several item {} and items {} sections. Keys must be unique and Bundle-compatible, or state restoration crashes.

6. State hoisting

Often asked as: “What is it, and why?”, “Where do you hoist state to?”, “stateful vs stateless composables”.

Explain it.

State hoisting moves state out of a composable and into its caller, so the composable becomes stateless. It receives a value and an onValueChange callback. The pattern is state flows down and events flow up. The benefits are a single source of truth, reuse, previews, easy testing, and sharing state between siblings.

@Composable
fun SearchBar(query: String, onQueryChange: (String) -> Unit) {       // stateless
    TextField(value = query, onValueChange = onQueryChange)
}

@Composable
fun SearchScreen(viewModel: SearchViewModel = hiltViewModel()) {        // stateful host
    val ui by viewModel.ui.collectAsStateWithLifecycle()
    SearchBar(query = ui.query, onQueryChange = viewModel::onQueryChange)
}

How high do you hoist?

  • At least to the lowest common ancestor of all composables that read or write the state.
  • UI element state, such as scroll position or expanded or collapsed, belongs in a plain state holder class exposed through a rememberXState() function.
  • Screen and business state belongs in the ViewModel. Do not pass the ViewModel into child composables: pass state and lambdas.

Trap: hoisting too far causes needless recomposition of large subtrees. Hoisting too little duplicates state. Offer a default parameter, such as state = rememberXState(), so simple callers stay simple.

7. Compose lifecycle

Often asked as: “What is the composable lifecycle?”, “What are the three phases?”, “identity”, “ComposeView in Fragments”.

What is the lifecycle of a composable?

Enter the composition, recompose zero or more times, then leave the composition. Effects and remember values exist only between entering and leaving. Identity is the call site and its position in the tree. key(id) { } gives explicit identity, which is used in lazy lists and in loops whose items reorder.

What are the three phases of each frame?

  1. Composition: decides what to show by running composables and building the tree.
  2. Layout: measures and places each node.
  3. Drawing: renders the result.

A state read in one phase invalidates that phase and the later ones. That is why lambda modifiers such as offset {} and drawBehind {} are cheaper: reads in layout and drawing skip composition.

How does it relate to the Android lifecycle?

A composition lives as long as its host, which is a ComposeView or an Activity. It is not stopped at onStop. Collect state with collectAsStateWithLifecycle(), and react to lifecycle events with LifecycleEventEffect. In Fragments, set ViewCompositionStrategy.DisposeOnViewTreeLifecycleDestroyed, so the composition is disposed along with the Fragment's view.

Trap: assuming composables run once, or in order. Never mutate shared variables or log analytics in the body, because it runs on every recomposition, and some of those runs get discarded. Use effects instead.

8. Navigation

Often asked as: “How do you structure navigation?”, “How do you pass arguments?”, “ViewModel scope”, “bottom bar state”.

How does Navigation Compose work in practice?

  • NavHost(navController, startDestination) with composable destinations. You use one Activity and many destinations.
  • Type-safe routes with Kotlin Serialization: @Serializable data class Detail(val id: Long), then navController.navigate(Detail(5)), and backStackEntry.toRoute<Detail>() to read it back.
  • Pass IDs, not objects. Load the data inside the destination's ViewModel. That survives process death and keeps arguments small.
  • hiltViewModel() inside a destination scopes the ViewModel to its NavBackStackEntry. For state shared by several screens, scope the ViewModel to a nested graph's entry.
  • Bottom bar: navigate(route) { popUpTo(start) { saveState = true }; launchSingleTop = true; restoreState = true }.
  • Deep links are declared per destination. Nested graphs map to features or modules.
NavHost(navController, startDestination = Home) {
    composable<Home> { HomeScreen(onOpen = { id -> navController.navigate(Detail(id)) }) }
    composable<Detail> { DetailScreen(onBack = navController::navigateUp) }
}

Trap: do not pass NavController down the tree. It hurts previews and tests. Expose callbacks such as onOpen instead. Collect one-off navigation events once, inside LaunchedEffect. Navigation 3 is a newer library in which you own the back stack as state. Mention it as awareness, and check the current documentation for its status.

9. Material Design 3

Often asked as: “How is theming done?”, “Dynamic colour”, “Adaptive layouts”, “edge-to-edge”.

What should a Material 3 answer cover?

  • Theme: MaterialTheme(colorScheme, typography, shapes). Read values through MaterialTheme.colorScheme.primary, never hard-coded colours.
  • Colour roles: primary, onPrimary, primaryContainer, secondary, tertiary, surface, surfaceVariant, error. The “on” colours guarantee contrast against their base colour.
  • Dynamic colour (Android 12 and later): dynamicLightColorScheme(context) derives the palette from the wallpaper. Fall back to a static scheme below API 31.
  • Dark theme follows isSystemInDarkTheme(). CompositionLocals such as LocalContentColor propagate defaults.
  • Components: Scaffold, TopAppBar, NavigationBar, ModalBottomSheet, FilledTonalButton, Card.
  • Adaptive UI: WindowSizeClass, plus NavigationSuiteScaffold or list-detail layouts for tablets and foldables.
  • Edge-to-edge: call enableEdgeToEdge() and handle WindowInsets, through Scaffold padding and imePadding.
@Composable
fun AppTheme(dark: Boolean = isSystemInDarkTheme(), content: @Composable () -> Unit) {
    val context = LocalContext.current
    val scheme = when {
        Build.VERSION.SDK_INT >= 31 && dark  -> dynamicDarkColorScheme(context)
        Build.VERSION.SDK_INT >= 31          -> dynamicLightColorScheme(context)
        dark                              -> DarkColors
        else                              -> LightColors
    }
    MaterialTheme(colorScheme = scheme, typography = AppTypography, content = content)
}

Trap: mixing the M2 (androidx.compose.material) and M3 imports in one screen. Forgetting the Scaffold content padding lets content hide under the system bars. Build a design system as a thin wrapper over M3 tokens, rather than scattering literal values.

10. Compose testing

Often asked as: “How do you test composables?”, “The semantics tree”, “screenshot tests”, “synchronisation”.

How does it work?

Tests query the semantics tree, which is the same accessibility information that TalkBack uses, not pixels. createComposeRule() tests a pure composable. createAndroidComposeRule<MainActivity>() needs an Activity, and Hilt if you use it. The rule synchronises automatically with recomposition, animations and idling resources.

@get:Rule val rule = createComposeRule()

@Test
fun showsError_andRetries() {
    var retried = false
    rule.setContent { ErrorView(message = "Offline", onRetry = { retried = true }) }
    rule.onNodeWithText("Offline").assertIsDisplayed()
    rule.onNodeWithTag("retry_button").performClick()
    assertTrue(retried)
}

What do you emphasise?

  • Stateless composables are easy to test: pass state in and assert on the lambdas that come out. This is a payoff of state hoisting. Test ViewModels separately with fakes and runTest.
  • Finders: onNodeWithText, onNodeWithContentDescription, onNodeWithTag, onAllNodes. Assertions: assertIsDisplayed, assertTextEquals, assertIsEnabled. Actions: performClick, performTextInput, performScrollToIndex.
  • Use useUnmergedTree = true when merged semantics hide child nodes. Use waitUntil { } for async work, and mainClock to control animations.
  • Screenshot tests (Paparazzi, Roborazzi, Compose Preview Screenshot Testing) catch visual regressions on the JVM. Robolectric runs Compose UI tests without an emulator.
  • For Hilt UI tests, use HiltAndroidRule and replace modules with fake repositories.

Trap: finding nodes by visible text breaks when strings are localised. Use testTag for test-only hooks and content descriptions for accessibility. Tests that sleep instead of using waitUntil or idling are flaky.
