The universal frame: use it for every question

Interviewers test how you think, not definitions. Every answer below follows the same seven steps, so practise saying them out loud.

The seven steps

  1. Reproduce. Get the exact steps, device, OS version, build, network and data state. If you cannot reproduce it, use production data (Vitals, Crashlytics) to find the pattern, such as which devices or versions are affected.
  2. Collect evidence. Logs, stack traces, Perfetto traces, heap dumps, metrics and request IDs. Data before guesses.
  3. Locate the layer. Is it the app, the device or hardware, the network, or a backend service? Rule layers out quickly: does it fail on other devices, on other networks, or when the API is called directly with curl?
  4. Isolate the root cause. Form a hypothesis, change one variable at a time, and bisect by commit or feature flag until you can explain why, not just where.
  5. Fix. The smallest safe change that addresses the cause, not the symptom.
  6. Test and guard. Unit or instrumented tests, a benchmark, StrictMode or LeakCanary in debug builds, and a staged rollout.
  7. Monitor. Watch the metric that proved the problem, and confirm it moved in production.

How to sound senior: think aloud. Ask clarifying questions first, such as “Does it happen on all devices? Since which release?” Prioritise by user impact, such as crash-free rate or the share of affected users. Mention a trade-off, and close with “I would add a guard so it cannot silently come back.”

1. Investigating an ANR

Often asked as: “Users report the app freezes. Walk me through it.”

What is an ANR?

The main thread fails to respond in time. The triggers are an input event not handled within about 5 seconds, a broadcast receiver running too long (about 10 seconds in the foreground, 60 in the background), or a service that does not start in time. Play Vitals tracks the ANR rate that users actually experience.

How do the seven steps apply?

  1. Reproduce: which screen and action, which device class, cold or warm start. Try with throttled CPU, large data sets and airplane mode.
  2. Collect: the ANR clusters in the Play Console or Crashlytics, with main-thread stack traces. Also adb bugreport or the traces in /data/anr. From API 30, ApplicationExitInfo with REASON_ANR lets you log ANRs yourself.
  3. Locate the layer: read the main thread state. Blocked means a lock is held by another thread. Native or binder means a slow system service or IPC. Runnable means CPU-heavy work. Waiting can mean SharedPreferences or QueuedWork. Check overall CPU load too.
  4. Root cause: find who owns the lock, which call is running on main, and the long slices in the Perfetto timeline.
  5. Fix: move disk, network and database work off main with coroutines and Dispatchers.IO. Use goAsync() or WorkManager in receivers, split large work, remove lock contention, and replace blocking binder calls.
  6. Test: enable StrictMode (detect disk reads, writes and network) in debug builds, and measure the flow with a macrobenchmark.
  7. Monitor: the ANR rate per version and device in Vitals, after a staged rollout.

What are the typical root causes?

  • Disk, database or network work on the main thread, huge JSON parsing, or SharedPreferences.commit() blocking in onStop.
  • Lock contention or deadlock between the main thread and a background thread, or runBlocking on main.
  • Heavy work in BroadcastReceiver.onReceive, Application.onCreate or a ContentProvider's initialisation.
  • A slow binder call to a system service, or a foreground service that does not call startForeground() in time.

Trap: the stack in an ANR report is the main thread at the moment the system noticed, which is not always the cause. It may be waiting for a lock held elsewhere, so look at all threads. Low-end devices under memory pressure also cause ANRs even with correct code.

2. Identifying memory leaks

Often asked as: “Memory keeps growing, or we get OOM crashes. What do you do?”

How do the seven steps apply?

  1. Reproduce: repeat a flow, such as opening and closing a screen or rotating, 10 to 20 times while watching memory. adb shell dumpsys meminfo <package> shows Activity and View counts.
  2. Collect: LeakCanary in debug builds reports the reference chain automatically. The Android Studio Memory Profiler can force a GC, capture a heap dump, and filter by the Activity or Fragment class to find instances that should already be gone.
  3. Locate the layer: Java heap, native memory or graphics (bitmaps). Is it a leak, where objects are retained forever, or bloat, where too much is legitimately alive, such as huge bitmaps?
  4. Root cause: read the path from a GC root to the leaked object, and find who holds the reference.
  5. Fix: break the reference by unregistering, cancelling, clearing it, using the application context, or a lifecycle-bound scope.
  6. Test: LeakCanary assertions in instrumented tests, then repeat the flow and compare heap dumps.
  7. Monitor: the OOM rate and “excessive memory” in Vitals or Crashlytics, and memory metrics per release.

What are the classic leak sources?

  • A static or singleton holding a Context, View or Activity. Use applicationContext.
  • Listeners, callbacks or receivers never unregistered. A Handler with delayed messages. Anonymous or inner classes that capture this.
  • Coroutines in GlobalScope, or in a scope that outlives the screen. Unclosed Rx subscriptions, and flows collected without a lifecycle.
  • A Fragment's view binding not cleared in onDestroyView. Adapters or RecyclerViews holding views, WebViews, and large bitmaps that are not sized or recycled.

Trap: “the GC did not free it” is not always a leak. Caches such as LruCache and bitmaps are retained by design. Compare heap dumps after forcing a GC. Mention that you also drop caches in response to onTrimMemory.

3. Analysing crashes

Often asked as: “The crash rate jumped after the release. What do you do?”

How do the seven steps apply?

  1. Triage first: how many users, which versions, devices and OS releases, and since when? High impact and new in this release means you consider halting the rollout or turning off a feature flag, before deep investigation.
  2. Collect: the Crashlytics or Vitals stack trace, deobfuscated with the R8 mapping file, plus breadcrumbs, custom keys such as the current screen, and logcat for a local reproduction. For native crashes, use the tombstone and ndk-stack with symbols.
  3. Locate the layer: your app, OS or OEM behaviour, a third-party SDK, bad server data, or resource exhaustion such as OOM?
  4. Root cause: read the Caused by: chain from the bottom up to the first line in your own package. Find the input that triggers it, and bisect against recent commits.
  5. Fix the cause, not a blanket try/catch.
  6. Test: write a failing unit or instrumented test first, make it pass, then roll out in stages.
  7. Monitor: crash-free users and sessions for the new version, with an alert on regressions.

Which crash types are common on Android?

  • NullPointerException from Java or platform types, or from JSON. IllegalStateException: Can not perform this action after onSaveInstanceState from fragment transaction timing.
  • OutOfMemoryError, TransactionTooLargeException (too much data in a Bundle or Intent), and NetworkOnMainThreadException.
  • Process-death restore where lateinit or static state is gone. ClassCastException or NoSuchMethodError from R8 shrinking or library mismatches. Permission and foreground-service restrictions on newer OS versions.

Trap: an obfuscated trace is useless without the uploaded mapping file. Crashes concentrated on one OEM or OS version usually mean a platform behaviour change, not your logic. Check the release notes and the behaviour changes that come with your target SDK.

4. Slow application startup

Often asked as: “Cold start takes six seconds on a mid-range phone. What do you do?”

How do the seven steps apply?

  1. Reproduce and baseline: define cold, warm and hot starts, and measure on a low or mid-range device with a release build. The key metrics are TTID, time to the first frame (the “Displayed” logcat line, or adb shell am start -W), and TTFD, time to full drawing (call reportFullyDrawn()).
  2. Collect: a Macrobenchmark with StartupTimingMetric for repeatable numbers, a System Trace in Perfetto or Android Studio, and the Play Vitals startup times. A cold start of 5 seconds or more is flagged as bad.
  3. Locate the layer: process creation, then Application.onCreate, ContentProviders and SDK initialisation, then the first Activity's onCreate, the first frame, and data loading. Which slice is the longest?
  4. Root cause: in the trace, look for long main-thread slices: SDK initialisation, dependency graph construction, disk reads, layout inflation, and class loading.
  5. Fix: defer or lazily initialise non-critical SDKs. Use the App Startup library instead of many ContentProviders, and lazy injection such as Lazy or Provider. Move work off main, and show cached content first. Add Baseline Profiles with ProfileInstaller, enable R8, simplify the first screen's layout, and use the Splash Screen API.
  6. Test: rerun the macrobenchmark, compare the median and P90, and add it to CI to catch regressions.
  7. Monitor: startup time percentiles per version and device class in Vitals or Firebase Performance.

Trap: measuring a debug build or a flagship device hides the problem. The first run is slow because of JIT warm-up, so choose the CompilationMode in benchmarks deliberately. Moving work to a background thread does not help if the first screen still waits for its result.

5. Diagnosing UI rendering issues

Often asked as: “The list scrolls janky”, or “animations drop frames”.

How do the seven steps apply?

  1. Reproduce: which screen and gesture, the device's refresh rate (60 Hz gives 16.6 ms per frame, 120 Hz gives 8.3 ms), a low-end device, and a release build.
  2. Collect: the Perfetto frame timeline or Android Studio's system trace, JankStats, the Macrobenchmark FrameTimingMetric, the Profile GPU Rendering bars, and the slow and frozen frame counts in Vitals. A slow frame takes over 16 ms, and a frozen frame takes over 700 ms.
  3. Locate the layer: which phase used the budget: the main thread (input, composition, layout or measurement), the RenderThread or GPU (drawing, overdraw, large bitmaps), or garbage collection pauses?
  4. Root cause: long Choreographer#doFrame slices, deep view hierarchies in Layout Inspector, and for Compose, recomposition counts and the compiler stability reports.
  5. Fix: remove work from the frame by moving it to the background or precomputing it. Flatten layouts or use ConstraintLayout. Use DiffUtil or ListAdapter instead of notifyDataSetChanged. Use stable keys and immutable items in lazy lists, right-sized cached images, and fewer expensive effects such as blur, shadows and alpha layers.
  6. Test: compare before and after frame-time histograms at P50, P90 and P99, not just “it feels smoother”.
  7. Monitor: JankStats telemetry, and the share of slow frames in Vitals.

Trap: optimising the average hides the worst frames that users notice, so look at P90 and P99. Jank during the first scroll is often JIT or class loading, which Baseline Profiles address. A GC pause appears as a gap with no app work, so reduce allocations in drawing and scrolling paths.

6. How hardware limits affect apps

Often asked as: “How do you build for the long tail of low-end devices?” A design-thinking question.

LimitEffectWhat you do

How do you answer?

Design for the weakest device you support, then enhance. Define device tiers with isLowRamDevice() or the memory class. Reduce features such as image quality and animations on low tiers. Test on a real low-end phone, and use Vitals to see which devices have the worst ANR, crash and jank rates.

Trap: “it works on my Pixel” is not evidence. Emulators do not reproduce thermal throttling, flash speed or OEM background killers.

7. Investigating network failures

Often asked as: “Some users get errors loading the feed. How do you find out why?”

How do the seven steps apply?

  1. Reproduce: which endpoint, which networks (Wi-Fi, cellular, VPN, corporate proxy), which regions, app versions and OS versions. Simulate bad networks with emulator throttling, a proxy's throttle, or toggling airplane mode.
  2. Collect: Android Studio's Network Inspector, Charles or mitmproxy, an OkHttp logging interceptor (debug only, with tokens redacted), and an OkHttp EventListener for DNS, connect, TLS and time-to-first-byte timings. Send correlation IDs in headers and match them to server logs.
  3. Locate the layer: app, network or server. Replay the same request with curl or Postman from the same network. Check server dashboards for 5xx errors. Compare with other users and devices.
  4. Root cause: classify the exception or status code:
    • UnknownHostException means DNS or offline. SocketTimeoutException means a slow or unreliable network or server. ConnectException means the server is refusing the connection.
    • SSLHandshakeException can mean a wrong device clock, an expired or mismatched pinned certificate, an old TLS version, or a proxy intercepting traffic.
    • 401 means an expired token or a refresh bug. 403 and 404 mean permissions or routing. 429 means rate limiting. 5xx means the backend.
    • Parsing errors suggest an API contract change. Blocked cleartext traffic points to the Network Security Config.
  5. Fix: sensible timeouts. Retry with exponential backoff and jitter, and only for idempotent requests. Use a token-refresh authenticator, clear error states for the user, caching with offline-first design through Room, backup certificate pins, HTTP/2 and compression. Map errors to a sealed type.
  6. Test: MockWebServer for failure cases such as timeouts, 500 errors, malformed JSON and slow bodies. Add an integration test through a flaky-network proxy.
  7. Monitor: Firebase Performance or custom metrics for success rate, error-type breakdown, and p95 latency per endpoint and per network type. Alert on spikes.
class TimingListener : EventListener() {
    override fun dnsEnd(call: Call, domain: String, addresses: List<InetAddress>) = log("dns done")
    override fun secureConnectEnd(call: Call, handshake: Handshake?) = log("tls done")
    override fun responseHeadersStart(call: Call) = log("time to first byte")
}

Trap: blind retries of non-idempotent POST requests can charge a card twice or duplicate data, so use idempotency keys. Retrying everything at once during an outage causes a retry storm, so add jitter and a cap. Logging full request bodies in production leaks user data.
