1. MVVM

Often asked as: “What are the responsibilities of each layer?”, “Why a ViewModel and not a Presenter?”, “Can a ViewModel hold a Context?”

Explain MVVM.

  • Model: data and business rules (repositories, entities, use cases). It knows nothing about the UI.
  • View: Activity, Fragment or Composable. It renders state and forwards user events, with no business logic.
  • ViewModel: holds UI state, exposes it as observable streams, handles events and calls the data or domain layer. It holds no reference to the View, the Activity or a View Context.

The flow is events go up, state comes down: unidirectional data flow.

Why does a ViewModel survive rotation?

It is stored in a ViewModelStore owned by the Activity or the navigation back-stack entry. The store survives configuration changes and is cleared only when the owner finishes permanently (onCleared()). It does NOT survive process death. Use SavedStateHandle for small state that must survive it.

@HiltViewModel
class OrdersViewModel @Inject constructor(private val repo: OrderRepository) : ViewModel() {
    private val _ui = MutableStateFlow<OrdersUi>(OrdersUi.Loading)
    val ui: StateFlow<OrdersUi> = _ui.asStateFlow()

    fun onRefresh() = viewModelScope.launch { _ui.value = repo.load().toUi() }
}

Trap: MVVM vs MVI. MVI keeps a single immutable state and explicit intents, which makes state easy to reproduce. You can use MVVM with a single UiState and get most of that benefit. Do not expose a MutableStateFlow publicly, and do not pass the ViewModel deep into child composables: pass state and lambdas instead.

2. Clean architecture

Often asked as: “Describe the layers and the dependency rule”, “Is a use case always needed?”, “Where do mappers go?”

Describe the layers.

  • Presentation: UI and ViewModel. Depends on the domain layer.
  • Domain: a pure Kotlin module with entities, repository interfaces and use cases. It depends on nothing Android-specific.
  • Data: repository implementations, remote and local data sources, DTOs and database entities. Depends on the domain layer.

The dependency rule: source-code dependencies point inward, toward the domain.

Do you always need use cases?

No. A use case earns its place when it holds real business logic, combines several repositories, or is reused by several ViewModels. A pass-through use case that only calls repo.getX() is boilerplate. Google's architecture guidance treats the domain layer as optional for this reason.

class GetFeedUseCase @Inject constructor(
    private val posts: PostRepository,
    private val users: UserRepository
) {
    operator fun invoke(): Flow<List<FeedItem>> =
        combine(posts.observe(), users.observe()) { p, u -> merge(p, u) }
}
// Models per layer: PostDto (network) -> PostEntity (Room) -> Post (domain) -> PostUi (screen)

Trap: separate models per layer cost mapping code. Justify them: API changes should not leak into the UI. Over-engineering a small app is a red flag, so say you scale the structure to the project.

3. Repository pattern

Often asked as: “Why a repository?”, “What is the single source of truth?”, “How do you design caching and error handling?”

What problem does it solve?

It hides where data comes from, whether network, database, cache or files, behind one interface. ViewModels and use cases do not need to know. It also makes testing easy with a fake repository, and it centralises caching, mapping and error handling.

How do you choose the source of truth?

The local database is the single source of truth. The UI observes the database through a Flow. The repository fetches from the network, writes to the database, and the UI updates automatically. The UI never reads a network response directly.

class ArticleRepositoryImpl @Inject constructor(
    private val api: ArticleApi,
    private val dao: ArticleDao
) : ArticleRepository {
    override fun observe(): Flow<List<Article>> =
        dao.observeAll().map { rows -> rows.map(ArticleEntity::toDomain) }

    override suspend fun refresh(): Result<Unit> = runCatching {
        dao.upsertAll(api.fetch().map(ArticleDto::toEntity))
    }
}

Trap: do not let the repository leak DTOs or Retrofit Response types upward. If you use runCatching inside coroutines, it swallows CancellationException: rethrow it. For pagination, Paging 3 with a RemoteMediator follows the same database-as-truth idea.

4. Dependency injection with Hilt

Often asked as: “Why constructor injection?”, “Hilt vs Dagger vs Koin”, “Scopes”, “@Binds vs @Provides”.

What is DI, and why constructor injection?

A class receives its dependencies instead of creating them. Constructor injection is preferred: dependencies are explicit, fields can be val and private, the class is easy to test with fakes, and it can never exist half-initialised. Field injection (@Inject lateinit var) is only for framework classes that you do not construct yourself, such as Activities, Fragments and Services.

What are the Hilt basics?

  • @HiltAndroidApp on the Application, @AndroidEntryPoint on Activities and Fragments, @HiltViewModel plus @Inject constructor on ViewModels.
  • @Module with @InstallIn(SingletonComponent::class). @Binds maps an interface to its implementation (cheaper, no generated body). @Provides creates third-party objects, such as Retrofit or Room, that you cannot annotate yourself.
  • Scopes: @Singleton (app), @ActivityRetainedScoped (survives rotation), @ViewModelScoped, @ActivityScoped. Unscoped bindings create a new instance each time.
  • Qualifiers, such as @IoDispatcher, tell apart bindings of the same type.
@Module
@InstallIn(SingletonComponent::class)
abstract class DataModule {
    @Binds abstract fun bindRepo(impl: ArticleRepositoryImpl): ArticleRepository
}

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides @Singleton fun provideRetrofit(): Retrofit = Retrofit.Builder().build()
}

Follow-up: Hilt is Dagger with a standard Android component hierarchy. Its graph is validated at compile time, so errors show up in the build. Koin is a service locator that resolves at runtime: simpler to start with, but failures show up only when the app runs. Inject dispatchers so tests can replace them.

5. Lifecycle

Often asked as: “What is the order of callbacks?”, “Fragment vs view lifecycle”, “Rotation and process death”, “lifecycle-aware collection”.

What is the Activity lifecycle?

onCreate → onStart → onResume (running), then onPause → onStop → onDestroy. Visible means started; interactive means resumed. Rotation destroys and recreates the Activity unless you handle configChanges. onSaveInstanceState is called before onStop on API 28 and later.

What is special about Fragments?

A Fragment has two lifecycles: the fragment itself (onCreate to onDestroy) and its view (onCreateView to onDestroyView). The fragment can outlive its view when it sits on the back stack. Null out the view binding in onDestroyView, and collect flows with viewLifecycleOwner, never this.

viewLifecycleOwner.lifecycleScope.launch {
    viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.ui.collect(::render)      // cancelled on STOP, restarted on START
    }
}
// Compose equivalent: val ui by viewModel.ui.collectAsStateWithLifecycle()

How does a ViewModel's lifecycle differ?

It is created on first use through by viewModels() and lives until its owner is permanently finished. It survives rotation but not process death. You can test process death with the “Don't keep activities” developer option, or with adb shell am kill. Persist IDs and inputs with SavedStateHandle, and keep real data in Room.

Trap: a plain lifecycleScope.launch { flow.collect {} } keeps collecting while the app is in the background. That wastes resources and can crash. Always use repeatOnLifecycle or collectAsStateWithLifecycle. Chapter {{ch:3}} covers this in depth.

6. State management: StateFlow, SharedFlow and LiveData

Often asked as: “StateFlow vs LiveData”, “How do you send one-time events?”, “stateIn and WhileSubscribed”.

StateFlowSharedFlowLiveData
Initial valueRequiredNot neededOptional
ReplayAlways the latest valueConfigurable (0 by default)Latest value
DuplicatesDropped (equal values)KeptKept
Lifecycle-awareNo (use repeatOnLifecycle)NoYes
Operators and threadsFull Flow operators, any threadFull Flow operators, any threadMain-thread centric

Which one for what?

  • StateFlow: UI state. It always has a current value.
  • SharedFlow: events with no “current value”. Events can be lost if nobody is collecting, since the default replay is 0.
  • LiveData: legacy and Java-friendly, lifecycle-aware, Android-only. In new code prefer Flow, which also works in the domain and data layers and in Kotlin Multiplatform.

How do you handle one-time events such as a snackbar or navigation?

The modern approach is to model the event as state and consume it. For example, an errorMessage: String? field is cleared once the UI has shown it. Nothing is lost on rotation or when nobody is collecting. Alternatives are a buffered Channel exposed with receiveAsFlow(), or a SharedFlow. Avoid the old SingleLiveEvent workaround.

val ui: StateFlow<UiState> = repo.observe()
    .map { UiState.Success(it) as UiState }
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), UiState.Loading)

Follow-up: WhileSubscribed(5000) keeps the upstream alive for 5 seconds, so a rotation does not restart it. It stops when the app goes to the background. Mutating a list in place emits nothing, because the reference is unchanged: always emit a new copy. MutableStateFlow.update {} is atomic.

7. Modularisation

Often asked as: “Why modularise?”, “How do feature modules talk to each other?”, “api vs implementation”, “dynamic features”.

Why modularise, and how?

Benefits: faster builds (parallel, and only changed modules recompile), enforced boundaries, team ownership, reuse and easier testing. A typical layout looks like this:

:app                      wiring, DI root, navigation host
:feature:home             UI and ViewModel, depends on core only
:feature:checkout
:core:domain  :core:data  :core:network  :core:database
:core:ui (design system)  :core:common  :core:testing

Features must not depend on each other. They share code through core modules, and talk through navigation contracts, deep links or a small :feature:x:api module of interfaces, wired together in :app with Hilt.

What about the Gradle details?

  • implementation hides a dependency from consumers, which speeds up incremental builds. api exposes it transitively, so use it sparingly.
  • Convention plugins in build-logic and a version catalog (libs.versions.toml) share configuration.
  • Dynamic feature modules are delivered on demand through Google Play to reduce install size. They are different from ordinary library modules.

Trap: too many tiny modules add configuration overhead. Avoid circular dependencies and a giant :core:common dumping ground. Modularise by feature first and by layer second. Hilt works across modules because the entry points in :app aggregate everything.

8. Offline support with Room and local data

Often asked as: “How do you design offline-first?”, “sync strategy”, “Room migrations”, “conflict handling”.

How do you design offline-first?

Room is the single source of truth, and the UI reads only from the database through a Flow. Writes go to the database first (optimistic) and are queued for sync. Reads trigger a background refresh. Connectivity, observed with ConnectivityManager.NetworkCallback, decides when to sync. It does not decide whether the app works.

How do you sync pending writes?

Mark rows with a sync status such as PENDING, SYNCED or FAILED, or keep an outbox table. Push them with WorkManager, which supports network constraints, exponential backoff, unique work, and survival across process death and reboot. Use idempotent requests with a client-generated ID so retries do not duplicate data. For conflicts, choose last-write-wins by timestamp or version, server-wins, or a field-level merge, depending on the product.

@Dao
interface ArticleDao {
    @Query("SELECT * FROM article ORDER BY ts DESC")
    fun observeAll(): Flow<List<ArticleEntity>>

    @Upsert
    suspend fun upsertAll(items: List<ArticleEntity>)

    @Transaction
    @Query("SELECT * FROM author WHERE id = :id")
    fun withPosts(id: Long): Flow<AuthorWithPosts>
}

What are the Room essentials?

  • The components are @Entity, @Dao and @Database. Queries are verified at compile time. DAO functions marked suspend or returning Flow run off the main thread.
  • Migrations: bump the version and provide a Migration or an AutoMigration. Never ship fallbackToDestructiveMigration() for user data. Export schemas and test migrations.
  • Add @Index on queried and foreign-key columns. Use @Relation or @Embedded with @Transaction for joins, and a TypeConverter for custom types.
  • Other local storage: DataStore for preferences and small settings (it replaces SharedPreferences), files, and encrypted storage for secrets.

Trap: do not load huge tables at once; use Paging 3 with a PagingSource. Multi-step writes need a @Transaction. Keep database entities out of the UI layer. For cache freshness, store lastFetched and refresh when the data is stale.
